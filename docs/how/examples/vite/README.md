# How the Vite example coordinates CodeMirror and WASM

[简体中文](README.zh-CN.md)

The Vite example is a browser client for the stateful WASM Analyzer. It demonstrates how one
application can coordinate analysis, editor help, CodeMirror presentation, and two independent
formula panels without moving those responsibilities into the Rust crates. This guide follows the
Current TypeScript implementation for maintainers who need to change or debug the example.

Everything described here about panel identity, debounce delays, grouped rows, chips, focus,
popover layout, and error fallback is **example policy**. It is not a stable product contract. The
user-visible guarantees belong to the
[editor-services specification](https://github.com/JoverZhang/notion-formula-rs/blob/master/docs/specs/editor-services.md)
and the
[WASM API specification](https://github.com/JoverZhang/notion-formula-rs/blob/master/docs/specs/wasm-api.md).
This guide explains how the demo consumes those surfaces; it does not redefine Analyzer, IDE, or
WASM algorithms.

## Startup creates one boundary client and two panel identities

[`main.ts`](../../../../examples/vite/src/main.ts) mounts the page shell and the static table, then
creates one `AppVM` and one `FormulaPanelView` for each member of `FORMULA_IDS`. The Current example
uses `f1` and `f2`. These values are DOM, view-model, and debug keys for demo panels; they are not
persistent formula identities from the formula domain.

Each panel is mounted with its own CodeMirror instance and sample source. `AppVM.start()` then
initializes a single WASM `Analyzer`, marks the application ready, and schedules any source already
recorded in the view model. In the Current startup those records are still empty, so the entrypoint
sends both sample sources through `setSource` after initialization. The view model, rather than the
initial DOM alone, thereby becomes the source of analyzed state.

```text
main.ts
  |
  +-- root layout + theme toggle
  +-- static table view
  +-- AppVM -------------------------- one configured WASM Analyzer
  |      |
  |      +-- FormulaState f1
  |      +-- FormulaState f2
  |
  +-- FormulaPanelView f1 ------------ CodeMirror instance f1
  +-- FormulaPanelView f2 ------------ CodeMirror instance f2
```

`FormulaState` in [`app/types.ts`](../../../../examples/vite/src/app/types.ts) carries the source,
diagnostics, tokens, output type, and an analysis status. `AppVM` owns those analysis-facing values
and one 80 ms timer per formula ID. The panel owns transient editor presentation such as selection,
completion rows, chip decorations, and popover visibility. Keeping these two kinds of state
separate prevents a focus change in one panel from overwriting the other panel's analysis result.

The table does not evaluate formulas. [`table_view.ts`](../../../../examples/vite/src/ui/table_view.ts)
renders fixed sample rows; `main.ts` only switches each formula column between `<error>` and
`<pending>` according to whether its analysis diagnostics contain an error. That placeholder is a
demo presentation choice, not an evaluator result.

## The WASM client is the only generated-module seam

[`analyzer/wasm_client.ts`](../../../../examples/vite/src/analyzer/wasm_client.ts) is the only
example module that imports wasm-pack glue. It keeps a module-level `initPromise` and `Analyzer`:

- A browser initialization lets wasm-pack load its own module URL.
- A Node initialization, used by Vitest, reads the `.wasm` bytes and passes them to wasm-pack
  because Node cannot fetch the generated `file:` URL.
- Repeated calls reuse the first promise and the same Analyzer. A rejected initialization promise
  is also retained, so the Current client has no retry path.

After initialization, `analyze`, `format`, `apply_edits`, and `help` are deliberately thin calls.
Calling one before initialization throws `WASM analyzer is not initialized`. DTO shapes are
imported from
[`analyzer/generated/wasm_dto.ts`](../../../../examples/vite/src/analyzer/generated/wasm_dto.ts),
while `src/pkg/` is generated by wasm-pack. The client should normalize host-side convenience, not
reimplement the Rust operations.

Help has one additional demo adapter. `buildCompletionState` turns absent completion or signature
fields into empty JavaScript values and drops non-number preferred-index entries; the row planner
performs the integer and bounds checks. Its safe wrapper catches any thrown help call and returns an
empty completion/signature state. This makes suggestion UI disappear on a boundary failure without
converting that fallback into a WASM guarantee.

## One edit drives two independent update loops

[`formula_panel_view.ts`](../../../../examples/vite/src/ui/formula_panel_view.ts) connects each
CodeMirror instance to two loops:

```text
document change
  |
  +-- onSourceChange -> AppVM -> 80 ms debounce -> analyze
  |                                      |
  |                                      v
  |                         diagnostics, tokens, output type
  |                                      |
  |                                      v
  |                            FormulaPanelView.update
  |
  +-- CodeMirror update -> 120 ms debounce -> help(source, selection head)
                                             |
                                             v
                              completion rows + signature popover

selection-only change -----------------------+
```

The analysis loop updates durable `FormulaState`. Immediately before the WASM call, `AppVM` emits
`analyzing`; a successful call replaces diagnostics, tokens, and output type and emits `ok`. Each
formula has its own debounce timer, so editing `f1` does not cancel an `f2` analysis.

The help loop is panel-local and runs after either a document or selection change. It always reads
the current CodeMirror document and selection head when its 120 ms timer fires. Completion state
can therefore update while a panel is inactive, but only the active panel renders it.

JavaScript strings and CodeMirror positions both use UTF-16 code units, matching the example-facing
WASM DTOs. The TypeScript client passes those positions directly. UTF-16-to-Rust conversion belongs
inside `analyzer_wasm`; the example must not add a second offset converter.

## Edit actions return to CodeMirror as one transaction

Completion items contain edits in original-document coordinates. `applyCompletionItem` in
[`wasm_client.ts`](../../../../examples/vite/src/analyzer/wasm_client.ts) rejects disabled or
edit-less items, combines the primary and additional edits, and sorts the resulting CodeMirror
changes by their original `(from, to)` coordinates. An explicit returned cursor wins. If it is
absent, the client places the cursor after the primary insertion and accounts for additional edits
ending at or before the primary start. `FormulaPanelView` dispatches the changes and selection
together, restores focus on the next animation frame, and requests fresh help.

Format and Quick Fix take a different route:

- Format passes the current source and selection head to `format`. If the returned source changed,
  the panel replaces the whole document and clamps the returned cursor to the new JavaScript
  string length.
- Quick Fix uses `firstDiagnosticAction` to select the first diagnostic action that retains at
  least one nonnegative, non-reversed range. It sends those edits to `apply_edits`, where the full
  boundary validation happens, then performs the same full-document replacement and cursor clamp.

The first-action rule, invalid-edit filtering, full-document dispatch, button labels, and silent
failure behavior are all demo decisions. Rust owns edit validation and application; the UI does not
try to reproduce overlap handling or cursor rebasing.

## Completion rows preserve result order while adding labels

[`model/completions.ts`](../../../../examples/vite/src/model/completions.ts) transforms completion
items into render rows without changing the item payload:

1. It accepts only distinct, in-range integer `preferred_indices` whose items are enabled, and
   emits those items once under `Recommended` in the supplied index order.
2. It walks the remaining enabled items in their existing order. Whenever the item `kind` changes,
   it inserts a human-readable group label before the next run.
3. Label rows have no selectable item. Selection helpers skip labels, wrap at either end, and
   normalize an invalid selection to an item row.

The resulting groups are presentation groups, not semantic categories promised by the IDE service.
Disabled items are omitted rather than rendered with their reason. The panel initially selects the
first selectable row, keeps the selection scrolled into view, applies it with Enter or Tab, moves
it with the arrow keys, and clears it with Escape. Mouse hover changes selection; clicking applies
the underlying completion item.

## Signature help and diagnostics share a popover

[`model/signature.ts`](../../../../examples/vite/src/model/signature.ts) renders the structured
signature segments delivered by WASM. It selects the requested signature with a first-signature
fallback, marks `Param` segments whose `param_index` equals `active_parameter`, and never parses a
display type string to recover parameter structure.

The unwrapped layout preserves segment order. The wrapped layout searches the segments before the
return arrow for an opening and closing parenthesis, then breaks parameter lines at comma segments
with a two-space indent. If those delimiters are absent it keeps the unwrapped layout.
[`signature_popover.ts`](../../../../examples/vite/src/ui/signature_popover.ts) first paints the
unwrapped form, measures overflow on the next animation frame, and repaints in wrapped mode when
needed. Its width is 28% of the viewport clamped to 240–360 px; it prefers the left side when that
side fits, otherwise the right side, then the side with more room.

The same popover can show diagnostic text below the signature. Diagnostic presentation in
[`model/diagnostics.ts`](../../../../examples/vite/src/model/diagnostics.ts) clamps ranges to the
CodeMirror document, maps known severities, and substitutes `(no message)` for an empty lint
message. The separate text list keeps the Analyzer's 1-based line and column and, when available,
adds a chip-coordinate range. These are two views over the received diagnostics, not a new
diagnostic ordering or de-duplication pass.

## Chips maintain a second presentation coordinate space

Token decorations and property chips are CodeMirror state fields defined in
[`editor_decorations.ts`](../../../../examples/vite/src/editor_decorations.ts) and
[`editor/chip_decorations.ts`](../../../../examples/vite/src/editor/chip_decorations.ts). State
fields map existing ranges through intervening document changes until the next analysis replaces
them, which keeps the editor coherent during the analysis debounce.

The example recognizes a chip only for the exact token pattern `prop("Name")` when `Name` is in
the configured property set. It replaces that complete range with an atomic CodeMirror widget.
Clicking a chip selects its raw start and returns focus to the editor. These recognition and
interaction rules are UI policy; they do not change property-reference syntax.

[`chip_spans.ts`](../../../../examples/vite/src/chip_spans.ts) validates sorted, non-overlapping,
in-bounds chip spans and builds a map that compresses each raw chip range to one display position.
If validation fails, the panel drops the chip map and chip decorations instead of exposing an
inconsistent coordinate space. Diagnostics intersecting a chip are expanded to the full atomic
range for CodeMirror and mark that chip in the UI. Valid chips can therefore remain visible even
when a later syntax error produces diagnostics elsewhere in the source.

## Focus owns suggestion visibility, not analysis

There is one module-level active panel ID and a registry of panel UI handles in
[`formula_panel_view.ts`](../../../../examples/vite/src/ui/formula_panel_view.ts). `focusin` activates
the panel, hides the previous panel's completion and signature UI, requests current help, and
renders it. `focusout` waits one animation frame before clearing activity so focus moves within the
same CodeMirror editor do not cause a flicker. A window resize only repositions the active
popover.

Losing focus hides suggestions but does not discard source, analysis results, editor history, or
the panel's latest completion state. Focusing another panel switches the visible suggestion owner;
it does not switch the shared WASM Analyzer configuration. This distinction is covered end to end
by
[`suggestions_panel_focus.spec.ts`](../../../../examples/vite/tests/e2e/suggestions_panel_focus.spec.ts).

## Failures are contained at the nearest demo boundary

The Current example intentionally uses different fallback policies at different layers:

| Failure | Demo response | Anchor |
| --- | --- | --- |
| WASM initialization rejects | `start()` rejects and the entrypoint logs the error; panels never become ready | `main.ts`, `AppVM.start` |
| Analyze throws after initialization | replace the result with one zero-width `analysis failed` diagnostic, clear tokens/type, and set `error` | `AppVM.runAnalyze` |
| Help throws | return empty completion and signature state | `safeBuildCompletionState` |
| Format or Quick Fix throws | leave the editor unchanged | button handlers in `formula_panel_view.ts` |
| Token or chip ranges are invalid | omit the unsafe decoration or chip mapping | `editor_decorations.ts`, `chip_spans.ts` |

These fallbacks keep the demo interactive and make failures observable at useful seams, but their
messages and silence are not compatibility promises. When a stable editor or WASM behavior is
wrong, fix its owning implementation or specification rather than encoding a compensating rule in
this client.

## Build and test the seam you changed

The example requires Node 20 or newer and pnpm 10. Scripts live in
[`package.json`](../../../../examples/vite/package.json):

- `wasm:build` runs wasm-pack against `analyzer_wasm` with the `web` target and writes `src/pkg/`.
- `dev`, `build`, and `preview` run the Vite lifecycle.
- `test` runs the 12 Vitest files; `test:e2e` runs the Chromium Playwright suite.
- `typecheck`, `lint`, `format`, and `check` cover TypeScript and frontend source quality.

The root [`justfile`](../../../../justfile) composes these commands. `just test-example-vite`
installs locked frontend dependencies, rebuilds WASM, then runs both Vitest and Playwright. Unit
tests isolate row planning, edit conversion, diagnostic/chip mapping, signature layout, and WASM
error adapters under
[`tests/unit/`](../../../../examples/vite/tests/unit/). Browser tests under
[`tests/e2e/`](../../../../examples/vite/tests/e2e/) exercise real focus, selection, history,
popover placement, UTF-16 cursor flow, decoration rendering, and the built WASM module.

[`playwright.config.ts`](../../../../examples/vite/playwright.config.ts) builds and serves a preview
for the suite. Unless `PW_PORT` is set, it hashes the checkout path into a port so parallel
worktrees are less likely to collide. Tests open the app with `?debug=1` and wait for
`window.__nf_debug` before inspecting a panel.

## Debug from the presentation boundary inward

Start with the layer that first owns the symptom:

- For focus, grouping, popover, button, or decoration behavior, inspect `formula_panel_view.ts` and
  the corresponding `src/model` or editor-decoration helper. Reproduce pure transformations in a
  Vitest test before involving the browser.
- For stale source, status, or cross-panel interference, inspect `AppVM` and its per-formula timers.
- For initialization, DTO shape, or a thrown host call, stop at `wasm_client.ts` and compare its
  generated DTO import with the built wasm-pack output.
- For a result that is transported correctly but semantically wrong, continue into the WASM, IDE,
  or Analyzer owner. Do not patch the result in the demo presentation layer.

[`debug/debug_bridge.ts`](../../../../examples/vite/src/debug/debug_bridge.ts) supports browser-level
inspection. It registers handles by formula ID and exposes source/status, Analyzer and CodeMirror
diagnostics, token and chip ranges, raw-to-chip coordinate mapping, and selection helpers through
`window.__nf_debug`. Registration is enabled in development and tests, or explicitly with
`?debug=1`; a normal production build without that query does not expose the bridge.
